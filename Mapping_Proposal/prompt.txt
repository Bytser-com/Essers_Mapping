RULE TYPES AND WHEN TO USE THEM
Choose exactly ONE primary rule_type for each target. Choose the operation that best describes how the target value or record is produced. Describe secondary conditions, transformations, lookups, and loops in their dedicated fields even when the primary type is different. The examples below illustrate the categories; they are NOT verified mappings or customer-specific rules.

- DIRECT: Copy a source value without meaningful change. Use when source and target have a clear semantic and datatype match, such as VBELN -> DELIV_NUMB. A matching field name or coincidentally equal value alone is insufficient. If an essential transformation, lookup, or qualifier-dependent decision determines the result, choose the more specific primary rule type. Review when business meaning may differ.
- FIXED: Populate a target with a constant, such as IDOCTYP = SHP_OBDLV_SAVE_REPLICA05. Use only for a confirmed, stable target control value or default applicable to the NEW customer. Check the target contract or reliable evidence; do not assume that a constant seen for another customer applies universally.
- DEFAULT_IF_EMPTY: Use a primary value and a clearly defined fallback only when the primary is empty or unavailable, for example LGORT with a fallback to ZLGORT. State the primary source, fallback source/value, what counts as empty, and the fallback order in transformation or condition. Confirm priority before approval.
- DERIVED: Construct a target using calculations, composition, or other derived logic, such as combining VBELN and POSNR to form a key. Specify all contributing source paths, concatenation order, separators, padding, or other processing in transformation. Do not invent a formula unsupported by evidence.
- CONDITIONAL: Populate a target only when an explicit business condition holds, for example selecting a date segment where QUALF = '006'. Specify the condition precisely, including which repeated record it applies to. If the central operation is a date-format conversion or a code lookup, consider FORMAT_DATE or LOOKUP as the primary type and still record the condition.
- LOOKUP: Translate a source code into a target code according to a mapping table, such as a possible PARTNER_Q -> PARTN_ROLE correspondence. Identify the lookup key, the required translation table or observed code pairs, and how unknown values are handled. Do NOT claim a lookup table or code translation exists unless supported; flag missing mappings for expert review.
- LOOP: Create repeated target records from repeated source records, such as E1EDL24 -> E1BPOBDLVITEM. Specify the source collection, target collection, parent-child boundaries, filtering, and record alignment in loop. Use LOOP as the primary type for a target field only when establishing repeated record generation is the defining mapping operation; for ordinary fields inside a loop, use the appropriate value rule type and ALSO explain the loop in the loop field.
- FORMAT_DATE: Convert a date or time into the required target representation, for example YYYYMMDD -> YYYYMMDDHHMMSS. State input format, output format, how time is obtained, and any timezone conversion. Appending '000000' is valid only if midnight is a confirmed requirement; it does not by itself establish a correct UTC timestamp.
- REVIEW_REQUIRED: A plausible mapping candidate or business rule exists, but its correctness cannot be established confidently. Describe the candidate (if any), the exact uncertainty, and what an expert must confirm. Set requires_review=true.
- NOT_MAPPED: No sufficiently supported source field, constant, derivation, or business rule can be identified for the target. Set source_path="", requires_review=true, explain what is missing in reason, and ask a precise review_question (for example, whether to leave the target empty, obtain another source, or define a default). NOT_MAPPED does NOT mean the field should necessarily remain empty in Essers' final implementation; it means the AI cannot establish a mapping from the available evidence.
